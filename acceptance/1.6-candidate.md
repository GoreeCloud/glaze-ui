# Glaze UI 1.6 Candidate Acceptance Record

## Release identity

- Candidate version: `1.6.0-candidate`
- Stable baseline preserved: `1.5.0`
- Candidate scope currently includes Evidence Presentation and Authority Surfaces plus Adaptive Workspace and Navigation.
- Glaze Motion remains Experimental and is not promoted by this Candidate.
- Smartwatch/wearable production support remains outside the current Stable form-factor contract and is not promoted by this Candidate.

## Candidate invariants

Glaze UI remains presentation and interaction authority. Privacy Shield, Wardveil Security, Everkeep, GoreeCloud Mesh, and application logic remain authoritative for the underlying privacy, security, continuity, coordination, availability, selection, validation, progress, completion, and workflow truth they produce.

A Candidate surface may present producer evidence and status but must not invent, strengthen, merge, or upgrade those claims through color, material, iconography, motion, layout, or prominence.

## Source validation

The 1.6 Candidate must pass the exact-revision Glaze UI CI stack, including retained 1.5 Stable validation plus the 1.6 evidence-presentation, workspace/navigation, Mesh evidence-consumer, refresh-response, and rendered Candidate gates.

Passing source validation does not by itself promote 1.6 or authorize production conformance.

## Adaptive Workspace source acceptance

`WORKSPACE_NAVIGATION.md`, `tokens/workspace-navigation.candidate.json`, `css/glaze.workspace.candidate.css`, `reference/candidate-1.6-workspace.html`, and `scripts/validate_workspace_navigation.py` define and enforce:

- semantic window, title, navigation, toolbar, content, inspector, status, and overlay regions;
- Desktop, Tablet, Mobile, Wide Desktop, and TV-specific composition behavior;
- persistent Desktop workspace chrome, adaptive Tablet navigation, Mobile overlay/sheet transformation, and a distinct far-view TV workspace that does not fall through to Wide Desktop;
- precision-pointer, mixed-input, coarse-pointer, and TV activation floors;
- comfortable, compact, and spacious density modes without weakening accessibility;
- logical semantic/focus order and current-destination/action-state preservation through responsive transformation;
- visible focus, keyboard access, no hover-only primary interaction, reduced motion, reduced transparency, forced colors, and no-backdrop/performance fallbacks; and
- explicit producer-authority boundaries.

## Rendered Adaptive Workspace acceptance

`reference/candidate-1.6-workspace-acceptance.html` and `scripts/validate_candidate_1_6_rendered.py` provide a fail-closed browser-rendered acceptance matrix for the Adaptive Workspace Candidate.

The matrix covers light and dark appearances for:

- Mobile `390×844`;
- Tablet `820×1180`;
- Desktop `1280×900`;
- Wide Desktop `1600×1000`; and
- TV `1920×1080`.

It additionally validates explicit compact Desktop and spacious Mobile density, reduced-motion Mobile behavior, reduced-transparency Mobile and Desktop behavior, performance-constrained Desktop fallbacks, and TV forced-colors behavior.

The rendered gate checks region visibility, root-overflow containment, semantic current-destination preservation, independent content scrolling, input-aware target floors, form-factor-specific transformation, TV-specific far-view sizing and non-overlay navigation, portable material fallbacks, density values, and accessibility-mode activation.

## Evidence Presentation acceptance boundary

`EVIDENCE_PRESENTATION.md` and its machine-readable/reference implementation remain part of the 1.6 Candidate. Promotion requires all evidence-presentation requirements in that contract to be satisfied, including representative rendered acceptance, accessibility/resilience cases, and consumer mappings for the applicable GoreeCloud platform systems.

The Adaptive Workspace rendered matrix does not substitute for those evidence-presentation-specific requirements.

## Platform-native boundary

The 1.6 Candidate design-system additions are platform-neutral contracts, tokens, CSS, JavaScript/reference code, and browser-rendered validation. The design-system repository does not ship a native Android, iOS/iPadOS/tvOS, Linux-native, television-hardware, or other platform-native workspace runtime as part of this Candidate.

Native GoreeCloud consumers must map the promoted semantics into their platform-native systems and complete application-specific native/real-device, accessibility, performance, focus/input, safe-area/overscan, and product-flow acceptance before claiming application conformance.

## Compatibility and migration

Glaze UI 1.5.0 remains the mandatory current Stable consumer target until 1.6.0 is explicitly promoted. Candidate evaluation must not trigger downstream migration or permit a Stable 1.6 conformance claim.

If 1.6.0 is promoted, the normal current-Stable rule applies: GoreeCloud-controlled user-facing applications must migrate through controlled, application-specific adoption and evidence-backed acceptance.

## Promotion decision

The release remains **Candidate**. Promotion is blocked until the complete 1.6 exact-head validation stack succeeds and all applicable 1.6 Evidence Presentation and Adaptive Workspace promotion requirements are complete and synchronized with `STABILITY.md`, `VERSION`, release metadata, consumer guidance, acceptance records, and rollback documentation.

## Rollback

Until Stable promotion, rollback is Candidate-level: revert or remove the 1.6 Candidate additions while preserving the 1.5.0 Stable baseline and without forcing consumer migration.

After any future 1.6.0 Stable promotion, rollback must use an explicitly documented release-level path and must not silently represent 1.5.0 as current conformance while 1.6.0 remains the declared Stable release.
