# GLAZE UI V1.1.1 Patch Candidate — Import Closure

## Status

**Lifecycle:** Release Candidate preparation  
**Candidate:** `1.1.1-rc.1`  
**Base Stable:** GLAZE UI V1.1 / `1.1.0`  
**Base Stable revision:** `15cc76d2bcd4065552dc31c77145b63f34d9e7b2`  
**Base immutable tag:** `v1.1.0`

This record describes a corrective candidate only. It does not alter the immutable `v1.1.0` release or establish `1.1.1` as Stable.

## Defect

The Stable V1 web graph reaches `css/glaze-v1.components.css` through `css/glaze-v1.0.0.css`. The component layer contained a stale import of `./glaze-v1.candidate.css`, but that path was never committed in the V1 namespace. The reset already carried the required foundation forward as `css/glaze-v1.foundation.css`, and the official V1 entrypoint loads that foundation before the component layer.

Strict CSS processors and asset pipelines therefore failed while resolving the published Stable graph even though earlier source-level release checks did not traverse import closure.

## Candidate repair

The candidate:

- removes only the stale Candidate dependency from the inherited V1 component layer;
- does not recreate a competing Candidate foundation;
- preserves the explicit `glaze-v1.foundation.css` load order in the official V1 entrypoint;
- adds recursive import-closure validation to the normal `scripts/validate_glaze_v1.py` path;
- rejects missing imports, remote imports, root escapes, query/fragment imports, symlinked targets, and import cycles;
- self-tests negative import cases before validating the repository graph.

## Acceptance boundary

Before a `1.1.1` Stable release can be claimed, this corrective source must receive fresh exact-revision source/build/rendered acceptance appropriate to the affected web graph, a reviewed Release Candidate identity, coherent release metadata, governed merge, independent post-merge main validation, a new immutable `v1.1.1` tag and GitHub Release, and canonical GoreeCloud documentation synchronization.

Because the dependency bytes change, downstream consumers must re-pin to the corrected immutable release and repeat applicable consumer-specific validation. Prior `1.1.0` consumer evidence remains historical evidence and is not silently rebound to the patch.

No downstream application becomes conformant, production-eligible, or Stable merely because this patch candidate passes Glaze repository CI.
